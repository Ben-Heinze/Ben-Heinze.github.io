* Mean vs Average
  The Statistical Sleuth uses /mean/ ($\mu$) when referring to an average calculated over an entire population, and /average/ ($\bar{\maths{Y}}$) when referring to the average in a sample, which is both a statistic and an estimate of the population mean.


* Parameter  

  A /parameter/ is an unknown numerical value describing a feature of a probability model and they are indicated by Greek letters like $\theta$. 

  A /statistic/ is any quantity that can be calculated from the observed data, and are represented by Roman letters.

  An /estimate/ ($\hat{\theta}$) is a statistic used as a guess for the value of a parameter


* Standard Deviation  
  The /Standard Deviation/ of a set of numbers $Y_{1}, \ldots, Y_{n}$ is defined as 
  \[
    \sqrt{\frac{\left( \sum_{i=1}^{n} (Y_i - \bar{Y})^{2} \right)}{(n-1)}}
  \]

  $\theta$ is the symbol for a population standard deviation, and $\its s$ is the sample standard deviation symbol.

* Standard Error
  The /standard error/ of any statistic is an estimate of the standard deviation in its sampling distribution. 

* Degrees of Freedom
  Associated with every standard error is a measure of the amount of information used to estimate variability, which is called /degrees of freedom/. The degrees of freedom (d.f.) are measured in units of "equivalent numbers of independent observations".


* Null and Alternative Hypotheses

  Hypothesis is a statistical method used to determine whether a treatment truly affects the outcome of an experiment or not. The null hypothesis is assuming that the treatment has no effect on the outcome of the study, while the alternative hypothesis claims there /is/ a change in results. 

  \[
  H_0: \delta = 0
  \]

  \[
  H_a: \delta \left( \leq,  \neq, \geq \right) 0
  \]


* p-value

  If the observed test statistic is improbably large under the null hypothesis, it suggests the null hypothesis is wrong - the treatment (not the randomization) caused the big difference. However, there's a chance that the randomization actually did cause the difference, and the chance of the randomization causing the improbably large test statistic is called (/observed/) /p-value/. 
  The /p-value/ from the randomization test is a probability statement that is tied directly to the chance mechanism used to assign subjects to treatkkkĸk

* Refined Demo Script (15 min)

** Introduction (~1 min)
Hello, my name is Ben Heinze, and together with Jordan I've been working on
modernizing CHARM. CHARM was previously a Java application; we rebuilt it with a
TypeScript frontend and a C++ backend, which gives us much faster computation
and a modern, responsive interface. CHARM is a risk-based prognostics and
health-management tool: it uses Bayesian Network and Continuous-Time Bayesian
Network, or CTBN, models to reason about faults, tests, and hazards across the
life of a system. Over the next fifteen minutes I'll walk through the core
tools, then bring them together with two examples: a vehicle model, and a
recreation of a real circuit-board test network. Let's start by launching the
application. {{{hl(purple,(LAUNCH CHARM))}}}

** The four tabs and building a network (~2.5 min)
CHARM is organized into four tabs, each with its own sub-tabs: Model, Editor,
Chart, and Risk.

The Model tab is where the network lives. The Model Editor is a graphical
canvas for hand-building a graph. To add a node, {{{hl(purple,drag a Test node,
a Fault node, a gate, and a Utility node from the palette onto the canvas)}}}.
To connect them, {{{hl(purple,click and drag from a parent node onto a child
node to create an edge)}}}. CHARM enforces the model's rules, so if I
{{{hl(purple,attempt an illegal edge, it's rejected)}}} and the network stays
valid. Then I can {{{hl(purple,click Apply Hierarchy Layout)}}} to arrange
everything into clean layers automatically. The palette provides fault nodes,
test nodes, three logical gates, conjunctive, disjunctive, and negation, and
utility nodes.

The Model Settings sub-tab holds model-wide options, most importantly the
inference engine, for example exact Variable Elimination, or a sampling engine
for large networks where exact inference would be too slow.

The Editor tab edits an individual node. {{{hl(purple,Selecting a node)}}} lets
you rename it, set its criticality, and name its states. Its Parameters sub-tab
adapts to the node type: priors and conditional probability tables for fault
nodes, intensity matrices for CTBN nodes, expressions for gates, and cost
functions for utility nodes.

The Chart tab is where we drive the model, and the Risk tab rolls everything up
into a risk matrix. Rather than keep building by hand, let me
{{{hl(purple,clear this graph)}}} and load a complete example.

** Vehicle Model (~9 min)
To see the tools working together, I'll load a pre-built example:
{{{hl(purple,Help -> Examples -> CTBN: Vehicle)}}}. This is a fresh,
factory-condition vehicle model: 14 faults, 7 hazard gates, 22 tests, and 16
utility nodes, with no observations and zero usage.

The model imported successfully, and the graph auto-arranged into layers.
Notice the hierarchy: the bottom layer holds the test nodes, the diagnostic and
utility nodes sit above them, and the hazard nodes sit at the top. Reading it
bottom to top is exactly how a technician thinks: the tests are the
measurements we can actually take, the faults are the underlying components
that might be degrading, and the hazards are the system-level consequences we
care about avoiding. If I {{{hl(purple,select a fault node and open the
Parameters tab)}}}, you can see its real prior, its conditional probability
table, and the intensity matrix that governs how it degrades over time, exactly
the values we described in the abstract. That intensity matrix is what makes
this a continuous-time model: rather than a single fixed failure probability,
each fault has a rate of transition that lets CHARM project its health forward
to any point in its service life.

Now to the Chart tab's Diagnostics view. It has two tables. The Test Node
States table lets us set the state of each test, and the Fault Nodes table
reports each fault's failure probability as a colored Value bar, its mean time
to failure, and its total accumulated usage. Let me {{{hl(purple,set the Air
System test and one more test to Fail)}}} to mimic a specific fault occurring,
and then {{{hl(purple,click Apply Inference)}}}. The Fault Nodes table now
updates: the Value bar shifts toward failure for the faults consistent with
those observations, and the MTTF and Total Usage columns fill in.

This is the core inference step, and it's the reason the C++ backend matters:
CHARM takes the evidence we just entered, propagates it through the entire
Bayesian network, and returns a calibrated posterior for every fault in
milliseconds, work that used to be noticeably slow in the old Java application.

Before deciding what to test next, I can {{{hl(purple,click Calc Info Gain)}}}.
This scores every test by how much information it would give us about the faults
we still can't distinguish, and {{{hl(purple,sorting that column)}}} puts the
most informative test at the top. That's a real workflow win: instead of
running through a fixed checklist, a technician always knows the single best
next measurement to take, which shortens troubleshooting time in the field.

Notice the graph nodes recolored themselves to match the test states and each
fault's risk. To dig into one, I'll open the Failure graph for the Air System
fault. At time zero the part is fresh, so its probability of failing is very
low; as usage accumulates, that probability climbs, and the vertical marker
shows where we are along that curve. If I {{{hl(purple,click "Show all fault
plots")}}}, CHARM previews every fault at once, each bordered by its current
risk: extreme in red, high in orange, medium in yellow, and low in green. The
{{{hl(purple,Hazard graph)}}} works the same way for hazard nodes, and the
{{{hl(purple,Utility graph)}}} shows how cost accumulates once a failure
occurs, which is what ties reliability back to dollars.

Now the Risk tab, which is where all of this comes together for a
decision-maker. When I {{{hl(purple,calculate risk)}}}, the matrix populates
with every diagnostic and hazard node, each placed by its likelihood on one
axis and its severity on the other. Likelihood is one minus the probability of
failure for diagnostic nodes, and the probability of the hazard for hazard
nodes; severity comes from the criticality we set back in the Node Editor. Cells
are color-coded from green for low risk up to red for extreme risk, and the
legend spells out the exact scoring bands. I can
{{{hl(purple,edit the likelihood thresholds)}}} to match a program's own risk
tolerance, {{{hl(purple,toggle between faults and hazards)}}} to switch between
component-level and system-level views, and {{{hl(purple,open the Bar Chart tab)}}}
to read the same data ranked. This single view is the payoff: instead of a wall
of probabilities, an operator sees at a glance what's most likely to fail and
how bad it would be if it did, and can prioritize maintenance accordingly.

That's a full loop on a fresh model. In practice you save these results, so
I'll briefly show {{{hl(purple,Save to file and Save to database)}}}, without
waiting on it. And here's why usage matters: I'll
{{{hl(purple,open a pre-saved model, vehicle-gen1.xml, that already has usage
greater than zero)}}}. Loading with accumulated usage reprojects the priors
forward and clears the earlier test observations, and you can see the MTTF
values shift accordingly, this is the same vehicle, one service interval later.
The identical snapshot also lives in our database, so
{{{hl(purple,loading it from the database by UUT, serial number, and
timestamp)}}} gives the exact same result as the file path. Finally, when a
part is physically swapped, {{{hl(purple,Replace System)}}} resets that fault's
usage to zero and restores its factory prior.
