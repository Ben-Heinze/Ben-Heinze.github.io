* Uniprogramming
Early memory management systems
- early computer systems supported one user and one program at a time (aka /uniprogramming/)
- To execute a program, the entire program had to be loaded continuously into main memory
- What are the implications?
  - Lots of wasted resources when waiting
  - Memory constraints are inefficient

The deck breaks that inefficiency down:
- The program size was /limited by the amount of available memory/
- If a program did not use all the allocated memory, the unused memory was /wasted/
- When the program was /waiting for an I/O operation/, the CPU remained /idle/
- As a result, /CPU and memory resources were often underutilized/

* Multiprogramming

In a /multiprogramming/ system, the user portion of memory must be divided to accommodate multiple processes.
- OS dynamically manages this division of memory (aka memory management)
- /Memory management/ (MM) determines how memory is allocated and used by different processes.

Some of the memory-management techniques we will study are relatively old and may not be used directly in modern systems. They still matter because they provide the fundamental concepts behind modern memory-management systems, and they help explain why modern operating systems use more sophisticated mechanisms. The underlying ideas are still valuable — learning them builds techniques and ways of thinking that apply to other problems.

* Memory Management Requirements


** Relocation

/Relocation: Ability to load program to any available part of the main memory. Access memory locations regardless of where its loaded./
- in multiprogramming system, available memory is shared among multiple processes
- Typically, programmers do not know in where the program will be in the main memory in advance
- Active processes need to be able to be swapped in/out of main memory in order to maximize processor utilization

This memory management requirement raises a lot of technical problems
- How can the programmer access memory without having to worry about relocation?

** Protection

/Protection: Ensure memory space allocated to the process you're running cant be accessed by unauthorized programs/

- Each process needs to be protected against unwanted access y other programs
- Relocation requirement makes harder to enforce protection since location of a program in main memory is unpredictable
- memory references generated by process must be checked at run time
- Processes need to acquire permission to reference memory locations for reading and writing purposes
- Schemes that support relocation must also support protection

** Physical Organization
/Physical organization: Managing the actual hardware memory (RAM, registers) to allocate and deallocate contiguous or non-contiguous blocks efficiently, addressing fragmentation challenges in early systems and optimizing resource use in modern ones/

- In earlier systems, the OS didn't have ability to move main program to from main memory to secondary memory. they used /overlaying/ where different program sections were loaded into the same memory... *(check notes later)*

Filling that in from the slides:
- Computer memory is organized in at least two levels: /main memory/ (fast, volatile, limited in size) and /secondary memory/ (slower, cheaper, much larger, non-volatile)
- Speed and cost trade off directly against each other: faster access means higher cost per byte — so fast memory is kept small and slow memory is made large
- The OS can exploit this by keeping programs in secondary memory when they aren't executing or are blocked on long I/O waits, freeing main memory for active work
- When the main memory available to a program is too small to hold it all at once, its code and data must be moved in and out during execution
  - In early systems this was the programmer's job — a technique called /overlaying/, where different program sections are loaded into the same memory region as they're needed
- Overlaying is impractical, and /relocation/ makes it worse: the programmer can't know ahead of time where in main memory the program will be placed, or how much space will be available (especially with multiprogramming)
- Therefore, moving information between the two memory levels must be the OS's responsibility, not the programmer's



* Fixed Partitioning


Fixed Partitioning Idea: partition memory into set of fixed partitions

First, assume the OS occupies portion of main memory, and the rest of the main memory is available for use by multiple processes
- two ways to partition memory:
  1. Equal sized partitions
  2. Variable sized partitions
- Any process whose size $\leq$ partition size can be loaded into the available partition.
- if partitions are full, and process is ready or in running state, the OS can swap a process out of any partition and loaded another process

He shows figure 7.2: example of fixed partitioning of a 64-Mbyte memory. One block is equal sized, and the other is variable sized. Equal-size is eight 8M partitions below the OS's own 8M; unequal-size is 2M, 4M, 6M, 8M, 8M, 12M, 16M.

** Equal sized partitioning
- program could be larger than the partition: programmer must use overlays to handle this problem
- Regardless of the size of the program, the entire partition is used by a particular process
- /internal fragmentation/: if you have a lot of small programs running, space is not utilized properly
  - Internal fragmentation occurs when a process is smaller than the partition it's allocated to — the leftover space inside the partition is wasted and can't be used by any other process

** Unequal sized partitioning
- Larger programs can be handled properly
- slightly better at handling smaller programs since we do have smaller partitions
- Can still have internal fragmentation

** Placement Algorithms

For equal sized partitions, as long as there is a free partition, you can load the program into it. If there are no available partitions swap a process already int the main memory to the secondary storage and load the new program to that partition

For unequal sized partitioning, assign the new process to the smallest available partition
- Use a scheduling queue for each partition, where each corresponding process will wait in the queue for the partition
- efficient in terms of low fragmentation, but (check notes later)

Finishing that thought from the slides: per-partition queues are efficient in terms of low fragmentation, because we always put the process into the best possible partition that minimizes internal fragmentation — but this is *not optimum from the point of view of the system*. Disadvantages:
- Wait time might be higher
- May need to swap processes to free up space

He shows an example where there are four partitions of varying sizes. The goal is to minimize internal fragmentation, but it doesn't efficiently utilize main memory, since programs are only being loaded based on size and not taking into account of available partitions.

The worked example: main memory is divided into four unequal partitions of 100 KB, 200 KB, 300 KB and 500 KB. Processes arrive needing 90 KB, 180 KB, 250 KB and 450 KB, and then P5 needs 150 KB.

*** One queue for everything
- We can also have one queue for all the processes
  - Then we allocate each process to the best available smallest partition in main memory
  - This improves the overall wait time
  - Obviously, if all the partitions are being used, we need to swap processes to free up space

** Disadvantages
- If your program is larger than all of the partitions, then {{{hl(red,overlays)}}} must be used
- {{{hl(red,internal fragmentation)}}}
- number of partitions specified at system generation time limits the number of active (not suspended) processes in the system




* Dynamic Partitioning

To overcome some problems in fixed partitioning, dynamic partitioning was introduced.

Partitions are of variable length and number.
- When a process is brought to memory, it is allocated exactly as much memory it requires

OS needs to keep track of boundaries of the partitions

/What happens when we use this strategy?/
- *External Fragmentation*: You will  see a lot of small holes in the main memory which cannot be occupied by processes.
  - To remove this, we use /compaction/, which squishes the processes in the main memory to remove the gaps in memory, giving you one continuous free space rather than small holes between the processes.

** Dynamic Placement Algorithms

Since compaction is time consuming and resource hungry the OS needs to be clever when choosing the best position for a process to reside in dynamic partitioning

For example, if there is more than one free block, which one should the OS use for placing the new process?

| Algorithm | Description | Worst case |
| Best-fit  | Chooses the block that is closest in size to the request        | $O(n)$. |
| First-fit | Begings to scan memory from the beginning and pics the first free hole the process will fit in | Worst one since it will quickly leave very small holes in memory, which requires compaction sooner than later|
| Next-fit  | begins to scan memory from the location of the last placement and chooses the next available block that is large enough. Once it reaches the end, it will go back to the beginning of the main memory (like best-fit but resumes from the last allocation) | Best option out of the three|

* Relocation - fixed vs Dynamic Partitioning
- A process will not always occupy the same place in memory over its lifetime
  - It can be swapped out to disk, then swapped back into a different partition or hole than before
  - Under dynamic partitioning, compaction can also shift a resident process to merge scattered free space
- Dynamic partitioning $\to$ relocation is *always* required
  - Swap-in lands the process in a different hole, and compaction moves processes around
- Fixed Partitioning $\to$ relocation is required *only if* a process can be reassigned to a different partition
  - Single queue for unequal partitions: the process may be reloaded elsewhere $\to$ relocation needed
  - Process always returns to its own partition, so its load address never changes $\to$ no relocation
- Consequence: The addresses a process references are *not fixed*
  - They change each time the process is swapped in or shifted
  - So addresses must be resolved at run time — via base (and bounds) registers

* Paging

Both unequal fixed-size and variable-size partitioning schemes use memory inefficiently
- /Fixed/: internal fragmentation (wasted space inside a partition)
- /Variable/: external fragmentation (holes between allocations)

/Paging/ eliminates external fragmentation and limits internal fragmentation.

- Partition memory into equal fixed-size chunks that are relatively small
- The process is also divided into small fixed-size chunks of the same size

| Term   | Meaning                      |
| Pages  | Chunks of a process          |
| Frames | Available chunks of memory   |

* Memory Management terms

| Term | Def |
| Frame | Fixed-length block of memory |
| Page  | fixed-length block of data that resides in secondary memory (such as a disk). A page of data may temporarily be copied into a frame of main memory. Paging doesn't require consecutive frames, so it's able to fill in the gaps (Hence elimiating external fragmentation)|
| Segment       | A variable-length block of data that resides in secondary memory. An entire segment may temporarily be copied into an available region of memory (segmentaiton) or the segment may be divided into pages which can be individually copied into main memory (combined segmentation and paging |




* Page Table

Maintained by OS, one for each process
- Maps each page in the process to the frames that it holds
  - (/page number $\to$ frame number/)
- Accessed by the processor via hardware mechanism that points to the current process's page table
- Used by processor to translate logical address into a physical address at runtime
- Used by the processor to produce the physical address
- page (and frame) size is always a power of 2
  - easier to convert logical $\to$ physical address
  - $\left[ \log_{2} \text{pages-size} \right] =$ the number of memory locations you have in a page, this is the maximum number of pages you can have in a process. If you have 16-bit address with a page size of 1kb, you'd have $\left[ \log_{2} 1024 = 10 \right]$ pages.

* Segmentation

A program can be subdivided into segments
- vary in length
- there's a max length

Segment table to represent the starting location and size of each segment loaded into the main memory

Addressing consists of two parts:
1. Segment number
2. Offset

Similar to dynamic partitioning. Eliminates internal fragmentation

- Visible to the programmer, unlike paging which is invisible
- provided as a convenience for organizing programs and data logically
- programmer or compiler assigns code and data to different segments (code, stack, heap, globals, etc)
- For modular programming, code/data may be split further into multiple segments
- Main drawback: Programmer must stay aware of the /maximum segments size/



** Address Translation

Another consequence of unequal size segments is that there is no simple relationship between logical addresses and physical addresses:

1. Extract segment number as the leftmost /n/ bits of the logical address
2. Use number to access process's segment table to find starting physical address of the segment
3. compare offset, express rightmost /m/ bits. If offset $\geq$ segment length, it is invalid
4. The desired physical address is the sum of the starting physical address of the segment plus the offset

* Virtual Memory

These are from the later (2026-09-11) lecture, not the memory management deck above.

Virtual memory: using secondary storage js if it were main memory (RAM). Virtual memory is provides the illusion that you have more than the available main memory.

/Resident set/: portion of the process in main memory


The OS can have a problem where once a process is needed in main memory when the main memory is full, it will have to swap out a process to make room for the new process. If this happens frequently, this can become a bottleneck for the processor since it spends more time swapping in/out processes rather than executing them. It's called /thrashing/ when an OS swaps instead of executes. To avoid this, you can try to predict which processes are least likely to be used in the near future.


** To make VM work:
  1. Hardware support for paging or segmentation
  2. OS must have software for managing movement of pages/segments between secondary memory and main memory


** Control Structure For Virtual Memory

Each process has its own page table

- Each /page table entry/ (PTE) contains the frame number of the corresponding page in main memory.
- Page table is needed for virtual memory with little bit more info on it


Page tables cannot be modified by its processees, only by the management software or else pointers will be inaccurate.


** How large can a page table be
{{{hl(red,TEST)}}}

Assume
- Address size = 32 bits
- Byte-level addressing (1 byte per addressable unit)
- Page seize  = 4kb = $2^{12}$ bytes
- Each page table entry = 4 bytes

Step 1: What is the max virtual address space?
- A 32-bit address can represent $2^{32}$ different addresses
- Since we have byte-level addressing:
  - $2^{32}$ bytes = *4GB*. Max virtual address space is 4gb.

- Step 2: How many pages can a process have?
  - Each page contains $2^{12}$ bytes
  - $\frac{2^{32} \text{bytes}}{2^{12}\text{bytes/page}} = 2^{20}$ pages
  - A process can have at most $2^{20}$ pages

- Step 3: How large can a page table be?
  - There is only one PTE for each page
  - Each entry is 4 bytes
    - $2^{20}$ entries $ \times 4$ bytes per entry = $2^{22}$ bytes = $4$ mb.
    - Therefore, tha max PTE size for one process is 4mb.

Now consider a system with many processes:
- if 1-- processes are runniing, and each has a 4mb page table:
  - $100b \times 4mb = 400mb$

In this example, every process needs a page table of 4mb.
