Deadlock detection (guaranteed question)

Uses Request Q (current requests), Allocation A, Available V. No claim matrix.

  1. Mark every process whose A row is all 0 (holds nothing, can't be in a deadlock).
  2. W ← V.
  3. Find unmarked Pi with Qi ≤ W (every column). None? stop.
  4. Mark Pi; W ← W + Ai; go to 3.

Deadlock ⟺ unmarked processes remain; the unmarked ones are deadlocked. Pick order doesn't matter.

Resource allocation graph

  • Circle per process; box per resource with one dot per instance (count from R).
  • Request edge P → R (asked, not granted): one per unit in Q.
  • Assignment edge R's dot → P (granted): one per unit in A.
  • Cycle + single instances = deadlock. Multiple instances: a cycle may not be a deadlock (6.5d); confirm with the algorithm.
  • RAG detection scales badly (node per instance) and handles divisible resources (memory) poorly.

Banker's algorithm (avoidance)

R (resources), V (available), C (claim = max), A (alloc). Need = C − A. Rj = Vj + ΣiAij.

Safety test: avail ← V; repeat: find Pk with Ck−Ak ≤ avail; avail += Ak, remove Pk. Safe ⟺ everyone removed. Final avail = R (sanity check).

Request: alloc+req > claim → error; req > avail → suspend; else pretend to grant, run safety: safe → grant, unsafe → restore + suspend.

Handout: V=(0,1,1); need P1(2,2,2) P2(0,0,1) P3(1,0,3) P4(4,2,0)
P2→(6,2,3) P1→(7,2,3) P3→(9,3,4) P4→(9,3,6) safe
Fig 6.8: P1 gets (1,0,1) → V=(0,1,1), all need R1 → unsafe

Safe = some order lets all finish. Unsafe ≠ deadlocked (only might be). Restrictions: max claims known in advance, independent processes, fixed # resources, no exit while holding.

I · Threads

  • Process = resource ownership (address space, protection) + scheduling/execution (state, priority). Separable.
  • Thread (lightweight process) = unit of dispatching. Process (task) = unit of resource ownership, "unit of resource allocation and protection".
  • Multithreading: many concurrent paths in one process. Single-threaded approach: thread not recognized. Java runtime = 1 process, many threads.
  • Per thread: state, saved context, execution stack, per-thread static storage, TCB, user + kernel stack. Shared: PCB, address space, resources.
  • Benefits: faster create, terminate, switch, cheaper communication (shared memory, no kernel).
  • Uses: foreground/background, asynchronous processing, speedup, modular structure.
  • Scheduled per thread. Suspend/terminate a process ⟹ all its threads.
  • States: Running, Ready, Blocked (no suspend). Ops: Spawn, Block, Unblock, Finish.

III · Mutual Exclusion

  • Race condition: shared data, ≥1 writer, result depends on timing. Critical section: code using shared resource. Mutual exclusion: only one in its CS at a time. Atomic: indivisible.
  • Livelock: keep changing state, no progress. Starvation: runnable but never chosen. Busy waiting = spin testing a variable.
  • Competing processes: mutual exclusion, deadlock, starvation. Concurrency ⊇ parallelism. Memory arbiter serializes access, no fairness.
  • Multiprogramming (1 CPU) / multiprocessing (multi CPU) / distributed processing.

Interrupt disabling: works on uniprocessor only; hurts efficiency. Compare&swap (atomic; returns old): while(cas(bolt,0,1)==1); CS; bolt=0; + any # processes, uni/multi, many CSs; − busy wait, starvation, deadlock.

Semaphore: init ≥0; semWait: count--; if <0 block; semSignal: count++; if ≤0 unblock one. Negative count = # waiting. Can't read it. Binary: 0/1. Strong = FIFO (no starvation), weak = unspecified. Must be atomic (hardware, Dekker/Peterson, CAS, interrupts). Mutex: locker must unlock (binary sem: anyone may signal).

Monitor: local data only via its procedures; enter by calling one; one process inside at a time. cwait(c) blocks + frees monitor; csignal(c) resumes one. Signals not saved (a semaphore count would remember).

IV · Concurrency Problems

Dining philosophers: 5 forks, need 2. Naive (sem per fork, left then right) → deadlock if all take left. Fix: 5 more forks, or room = 4 (wait(room) before forks, signal after). Monitor: cwait on ForkReady[i] per missing fork.

Producer/consumer: one at a time in buffer; no add when full, no take when empty.

  • Binary sems s=1, delay=0 wrong: consumer tests n==0 outside CS; stale delay signal → n = −1. Fix: m = n inside CS, test m.
  • Counting: n=0, s=1. Prod: wait(s) append signal(s) signal(n). Cons: wait(n) wait(s) take signal(s) consume.
  • Swap producer signals: OK. Swap consumer wait(n)/wait(s): deadlock.
  • Bounded: add e = size; prod wait(e) first; cons signal(e) after take.

Readers/writers: many readers OR one writer. Readers priority: wsem guards data, read_lock guards readcount; first reader waits wsem, last signals → writers starve. Writers priority: a waiting writer blocks new readers (readblock/rsem; writepending/z lets 1 reader queue on rsem) → readers starve. Neither: FIFO queue via semaphore.

V · Deadlock

Deadlock: permanent blocking of a set, each waiting on an event only another in the set can cause. Reusable (CPU, I/O channels, memory, devices, files, semaphores) vs consumable (interrupts, signals, messages; e.g. blocking Receive before Send). Fatal region in a joint progress diagram.

ConditionPrevent by
Mutual exclusiongenerally can't
Hold & waitrequest all at once (long waits, idle resources, foreknowledge)
No preemptionrelease on denial / OS preempts holder
Circular waitlinear ordering of resource types

First 3 necessary, not sufficient; all 4 = necessary + sufficient. Prevention: indirect (first 3) / direct (circular wait). Avoidance: process initiation denial or resource allocation denial (banker's). Detection: grant freely, check periodically (early detection, simple; costs CPU).

Recovery: abort all; back up to checkpoint + restart; abort one by one; preempt one by one. Integrated: classes ordered; swappable space = all at once; process resources = ordering/avoidance; main memory = preemption; internal = ordering. Linux/Windows mostly ignore deadlock.

VII · Key code

Semaphore primitives (Fig 5.6 / 5.7)

semWait(s): s.count--;
  if (s.count < 0) { put in s.queue; block; }
semSignal(s): s.count++;
  if (s.count <= 0) { move P from s.queue to ready; }
semWaitB(s): if (s.value == 1) s.value = 0;
  else { put in s.queue; block; }
semSignalB(s): if (s.queue empty) s.value = 1;
  else { move P from s.queue to ready; }

Atomic via CAS: spin on cas(s.flag,0,1) only around the primitive's few lines (not the whole CS). Via interrupts: inhibit, update, allow.

Dekker (P0; P1 symmetric) · init turn=1

flag[0] = true;
while (flag[1])
  if (turn == 1) {
    flag[0] = false;
    while (turn == 1) ;  /* wait */
    flag[0] = true; }
/* critical section */
turn = 1; flag[0] = false;

Only the process whose turn it isn't backs off → no livelock.

Bounded buffer (Fig 5.16) · s=1, n=0, e=size

producer: produce(); semWait(e); semWait(s);
  append(); semSignal(s); semSignal(n);
consumer: semWait(n); semWait(s); take();
  semSignal(s); semSignal(e); consume();

s = mutual exclusion on buffer; n = filled slots (consumer waits if empty); e = empty slots (producer waits if full).

Incorrect P/C (Fig 5.12) · s=1, delay=0, n=0

producer: produce(); semWaitB(s); append(); n++;
  if (n==1) semSignalB(delay); semSignalB(s);
consumer: semWaitB(delay); loop: semWaitB(s); take();
  n--; semSignalB(s); consume();
  if (n==0) semWaitB(delay);

Trace: consumer empties buffer (n=0), producer adds before the consumer's if (n==0) (n=1, delay=1), consumer skips the wait; next round its semWaitB(delay) eats the stale signal → takes from empty, n = −1. Fix (5.13): m = n; inside CS, if (m==0).

READER: wait(read_lock); readcount++;
  if (readcount==1) wait(wsem);
  signal(read_lock); READUNIT();
  wait(read_lock); readcount--;
  if (readcount==0) signal(wsem);
  signal(read_lock);
WRITER: wait(wsem); WRITEUNIT(); signal(wsem);

Writers priority (handout Alg 2)

readblock=writeblock=writepending=1; mutexes r_, w_
READER: wait(writepending); wait(readblock);
  r.lock; readcount++; if ==1 wait(writeblock); r.unlock;
  signal(readblock); signal(writepending); READUNIT();
  r.lock; readcount--; if ==0 signal(writeblock); r.unlock;
WRITER: w.lock; writecount++; if ==1 wait(readblock); w.unlock;
  wait(writeblock); WRITEUNIT(); signal(writeblock);
  w.lock; writecount--; if ==0 signal(readblock); w.unlock;

Stallings names: readblock = rsem, writepending = z. Readers only: wsem set, no queues. Writers only: wsem + rsem set, writers queue on wsem. Mixed: one reader queues on rsem, others on z, writers on wsem.

semaphore fork[5] = {1}, room = 4;
think(); wait(room); wait(fork[i]);
wait(fork[(i+1) mod 5]); eat();

IX · Commonly confused

  • Process vs thread. Process owns resources + protection; thread is what gets dispatched.
  • Deadlock vs livelock vs starvation. Blocked forever / busy but no progress / runnable but never picked.
  • Prevention vs avoidance. Prevention removes a condition by design; avoidance checks each request dynamically (safe state).
  • Avoidance vs detection. Claim matrix C, every request / request matrix Q, periodic + recovery.
  • Unsafe vs deadlocked. Unsafe = no guarantee; not yet deadlocked.
  • Cycle in RAG. Deadlock only certain with single instances.
  • Binary semaphore vs mutex. Anyone may signal a binary semaphore; only the locker unlocks a mutex.
  • Strong vs weak semaphore. FIFO (starvation-free) vs unspecified order.
  • Semaphore vs condition variable. Count remembers a signal; csignal with no waiter is lost.
  • SPN vs SRT. Same idea; SRT preempts on arrival using remaining time.
  • Concurrency vs parallelism. Overlap/interleaving vs truly simultaneous.
  • Indexed sequential vs indexed. Keeps sequential order + overflow file vs access only through indexes.
  • Chained alloc vs chained free portions. File's blocks linked vs free space linked.
  • Compaction vs consolidation. Contiguous (squeeze out holes) vs chained/indexed (bring a file's blocks together).
  • Preallocation vs dynamic. Max size at creation vs portions as needed.
  • Reusable vs consumable. Not depleted by use vs created and destroyed.

X · More file management

Objectives: meet user data needs, valid data, performance, many device types, minimize lost data, standard I/O routines, multi-user support. User requirements: create/delete/read/write/modify; controlled access to others' files and control of own; move data between files; back up/recover; access by name.

Criteria for an organization: short access time, ease of update, economy of storage, simple maintenance, reliability.

Indexed seq. lookup: search index for the highest key ≤ target, follow pointer, search main file sequentially from there. Multiple index levels for larger files.

Portion size: variable large contiguous (performance, small tables, like dynamic partitioning: best/next/nearest fit) vs small fixed blocks (flexible, bigger tables, contiguity abandoned).
